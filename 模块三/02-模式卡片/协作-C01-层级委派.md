# C01 层级委派

坐标：协作 × 层级　　落地形式：子智能体

## 是什么

总管拆任务、派给专门的子智能体，各自只拿到需要的上下文，再汇总结构化的结果。

## 放在哪一步

第 1、4 步：摘要素和核数字交给两个只读的子智能体，主智能体汇总。

## 供修改使用

交给 TRAE：“按这张卡，在项目里创建下面的文件，内容照抄，再按我们组的情况改。”

`.trae/agents/notice-reader.md`

```markdown
---
name: notice-reader
description: 当需要从 inbox 的通知里摘出合约、参数、新值、起用日期时调用
tools: Read, Glob, Grep
---

你只读通知，不修改任何文件。
对 inbox/ 里的每份通知，输出表格：通知编号 | 类型 | 合约 | 参数 | 原值 | 新值 | 起用日期 | 条款。
被更正过的那一行写明“已被第 N 号更正”。读不清的写“待确认”。
```

`.trae/agents/calc-checker.md`

```markdown
---
name: calc-checker
description: 当需要核对变更单里的价格和保证金是否算对时调用
tools: Read, Glob, Grep
---

你只核对数字，不修改任何文件。
对 draft/ 里变更单的每个价格，找到下面贴的 calc.py 命令和输出：
1. 命令里的基准价取自 data/结算价.csv 的哪一天；
2. 幅度、比例取自哪份通知的哪一条；
3. 变更单里的数和输出是否一致。
输出表格：合约 | 数字 | 输入来源 | 结论。看不出来的写“待确认”。
```

用的时候这样说：

```
先请 notice-reader 摘出 inbox 里全部通知的要素；起草变更单后，请 calc-checker 核对数字；把两份结果汇总在变更单末尾。
```

## 怎么看它起作用了

看两个子智能体是否各自只做自己的事，主智能体是否把两份结果汇总在变更单末尾。

## 代价

步骤之间强依赖、要共享大量中间结果时，拆开反而乱；子智能体的用量比单个对话高，小任务不值得。

## Qoder CN 配置

把上面的文件放到 `.qoder/agents/notice-reader.md`、`.qoder/agents/calc-checker.md`，front matter 保留 `tools: Read, Grep, Glob`。用 `/notice-reader`、`/calc-checker` 点名调用，确认调用记录里出现子智能体的卡片；提示词里写明主会话不修改文件，检查结束后看文件差异。

业务资料、输出格式和检查方法与上面 TRAE 的示例相同；两款工具的路径和工具名对照见本目录 README 末尾。
