# C03 对抗评审

坐标：协作 × 循环　　落地形式：子智能体

## 是什么

一方提案，独立的一方专门挑错，裁决者决定；靠不同的模型、不同的上下文保证独立。

## 放在哪一步

第 7 步提交审批之前：专门挑错。

## 供修改使用

交给 TRAE：“按这张卡，在项目里创建下面的文件，内容照抄，再按我们组的情况改。”

`.trae/agents/red-team.md`

```markdown
---
name: red-team
description: 变更单提交审批之前，专门找它可能出错的情况时调用
tools: Read, Glob, Grep
---

你只挑错，不修改文件，也不给出改好的版本。
读 draft/ 里的变更单、inbox/ 的全部通知和 data/交易日历.csv，找出这份变更单可能出错的三种情况，例如：漏看了更正通知、起用日期落在休市日、一般持仓和套期保值持仓写混。
每条写：情况 | 依据（文件与条款）| 严重程度。
```

用的时候这样说：

```
请 red-team 挑错；对每一条写“采纳”或“不采纳”和理由，改完再请它看一轮，最多两轮，最后由我裁决。
```

## 怎么看它起作用了

看 red-team 是否找出至少一条真实的问题，主智能体是否逐条回应。条件允许时，给挑错的一方换一个模型。

## 代价

低风险的日常改动不值得；挑错一方和起草一方用同一个模型、同一份上下文，挑不出同一个盲点。

## Qoder CN 配置

把上面的文件放到 `.qoder/agents/red-team.md`，front matter 保留 `tools: Read, Grep, Glob`。用 `/red-team` 点名调用，确认调用记录里出现子智能体的卡片；提示词里写明主会话不修改文件，检查结束后看文件差异。

业务资料、输出格式和检查方法与上面 TRAE 的示例相同；两款工具的路径和工具名对照见本目录 README 末尾。
