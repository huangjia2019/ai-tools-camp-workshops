# 提示词包

下午七个小练习的提示词，外加几条日常能用的。复制到 TRAE 里用，按自己的项目改掉下划线部分。

## 小练习：写一条项目规则，看它生效

```
在当前项目里新建规则文件 .trae/rules/参数变更.md，内容如下（照抄）：

# 参数变更规则

- 改动涨跌停板、保证金这类参数时，回复里写明依据：通知编号和条款。依据不全就列进“待确认”，不要猜。
- 价格和金额用 Decimal 或整数分计算，不用浮点数做比较。
- 不修改测试的期望值。期望值有疑问时，在回复里列出疑问，等人确认。
```

## 动手二：只读的规则核对员

```
在当前项目的 .trae/agents 目录下创建子智能体文件 price-checker.md，内容如下（照抄，不要改动）：

---
name: price-checker
description: 当用户要求检查涨跌停价、保证金等价格计算是否符合规则时调用
tools: Read, Glob, Grep
---

你是风控规则核对员，只读，不修改任何文件。
逐条检查三件事：
1. 涨停价不高于 结算价 ×（1 + 幅度），跌停价不低于 结算价 ×（1 - 幅度）；
2. 结果是最小变动价位的整数倍；
3. 价格计算没有用浮点数。
输出表格：检查项 | 结论 | 代码位置 | 依据。
看不出来的写“待确认”，不要猜。
```

## 动手三：参数变更复核技能

```
帮我在 .trae/skills 目录下创建一个技能，名字叫 param-change-review（参数变更复核）。

description：当用户要根据交易所通知修改涨跌停板、保证金等参数，或复核这类改动时使用；改变量名、调整界面样式时不要使用。

指令：
1. 从通知中摘出：品种、合约范围、参数新值、生效时点。缺任何一项就停下，列进“待确认”，不要猜。
2. 判定从哪个交易日起用：按通知原文的生效时点和交易日历判断，写出判断依据。
3. 同一合约同时适用几个比例时，按规则说明取哪一个，写出条款。
4. 每个测试期望值都写出计算过程，不许拿程序运行结果当期望值。
5. 输出一张变更单：参数 | 旧值 | 新值 | 起用时点 | 依据 | 待确认。
```

## 动手四：测试用例矩阵

```
为上午做的涨跌停价计算器设计测试用例矩阵，至少 8 条，覆盖：结果正好是整数倍、需要取整、不同幅度、非法输入（结算价不是正数、最小变动价位为 0）。

每条写：输入 | 期望涨停价 | 期望跌停价 | 计算过程 | 依据。
期望值必须按规则手算，不许先运行程序再把结果抄成期望值。

然后在页面上加一个“自测”按钮：逐条运行这些用例，显示通过或失败。
```

## 小练习：审三份上线材料

```
你是这次上线的审查员。请审查下面的改动，按“严重 / 一般 / 提示”列出问题，每条写：位置、问题、为什么、怎么改。
特别注意：测试期望值是怎么来的；SQL 是否有注入风险；接口是否校验了调用者的身份。
看不出来的写“待确认”，不要猜。

【材料】
（把材料 A、B、C 粘贴到这里；只贴 A，就只审 A）
```

## 日常能用的

### 把一次对话里的做法写成规则

```
把我们这次对话里确定下来的做法，整理成 .trae/rules/ 下的一份规则文件：每条一句话，写清楚要做什么、不做什么；只写以后每次都要遵守的，一次性的要求不要写进去。
```

### 把一个重复的任务写成技能

```
我每周都要做这件事：________。帮我写成一个技能，放在 .trae/skills/<名字>/SKILL.md：description 写清楚什么时候用、什么时候不用；指令写成编号的具体步骤；写明缺信息时停下来列进“待确认”。写完列出三句该触发和两句不该触发的话，我来测。
```

### 让子智能体只读地做一次检查

```
在 .trae/agents/ 下建一个只读的子智能体，名字叫 ________，只给 Read、Glob、Grep 三个工具，负责检查 ________。输出一张表：检查项 | 结论 | 位置 | 依据；看不出来的写“待确认”。
```

### 审查一次改动

```
审查当前分支相对 main 的全部改动，按“严重 / 一般 / 提示”列问题，每条写位置、问题、为什么、怎么改。特别看测试期望值的来源、SQL 拼接、接口有没有校验调用者。没看到的文件列出来，不要说“没有问题”。
```

### 检查 MCP 的数据新不新

```
用 MCP 查完以后，告诉我数据更新到哪一天、依据是哪份文件；如果问题里的日期晚于数据更新日期，明确说出来，不要直接给结论。
```
