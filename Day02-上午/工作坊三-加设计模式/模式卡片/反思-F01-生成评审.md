# F01 生成评审

坐标：反思 × 链式　　落地形式：子智能体

## 是什么

一个角色生成，另一个按证据和标准独立评审；评审的范围、轮次和成本都有上限。

## 放在哪一步

第 5 步之后：另一个只读的角色复核变更单。

## 供修改使用

交给 TRAE：“按这张卡，在项目里创建下面的文件，内容照抄，再按我们组的情况改。”

`.trae/agents/change-reviewer.md`

```markdown
---
name: change-reviewer
description: 当需要复核 draft/ 里的变更单时调用
tools: Read, Glob, Grep
---

你是变更单复核员，只读，不修改任何文件。
逐行检查：
1. 新值和通知原文一致；有更正通知的，以更正后的为准；
2. 每一行都写了依据（通知编号和条款）；
3. 价格下面贴了 calc.py 的命令和输出，数字一致；
4. 原值取自 prod/params.csv。
输出表格：行 | 结论 | 问题 | 依据。看不出来的写“待确认”，不要猜。
```

用的时候这样说：

```
请调用 change-reviewer 复核 draft 里的变更单。
```

## 怎么看它起作用了

起草完变更单后点名调用 change-reviewer，看它是否逐行给出结论。TRAE 里要点名调用才稳定。

## 代价

格式、算术这类能用程序检查的，先用程序；起草和复核用同一个上下文，容易沿用同一个错误假设。
